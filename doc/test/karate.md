## 1. ディレクトリ構成
標準として以下の構成をとる。
- `src/test/java/karate/`
  - `karate-config.js` : 環境変数（baseUrl, トークンなど）のグローバル設定
  - `common/` : 認証処理や共通のセットアップ処理（例: `auth.feature`）
  - `features/` : エンドポイントやドメインごとのテストシナリオ群

## 2. 実装ルール
- **1ファイル=1エンドポイント（リソース）**: テストの可読性と保守性を高めるため、原則として1Featureファイルにつき1リソースをテストする。
- **環境変数の利用**: リクエスト先ホストや認証情報は直接記述せず、`karate-config.js` で設定された変数（例: `baseUrl`）を使用する。
- **認証の共通化**: テストごとのログイン処理を省くため、`Background` 内で `callonce read('classpath:karate/common/auth.feature')` などを利用して認証トークンをキャッシュ・再利用する。

## 3. アサーション（検証）ポリシー
- **Shape（スキーマ）検証の優先**: 値の完全一致ではなく、Karateのファジーマッチャーを利用した「型と構造」の検証を優先する。（例: `#string`, `#uuid`, `#notnull`）
- **固定値の検証**: Enum、ステータスコード（200, 400等）、フラグなど、仕様上変わるべきでないものは完全一致で検証する。

## 4. DB連携とデータ検証
- **既存Java/MyBatis資産の再利用**: 
  テスト用にSQLを再定義しない。Java側に用意した共通のBean取得ヘルパー（例: `SpringContextHelper`）を経由して既存のMapperインスタンスを取得し、DBから直接データを取得する。
- **期待値JSONの組み立てと一括比較**: 
  レスポンスとDBの値を比較する際は、個別に検証するのではなく、DBから取得したEntityの値を `#()` 記法で埋め込んだ「期待値JSON」を定義する。
  この期待値JSONとAPIレスポンス全体を一括比較（`match response == expected`）することで、差分（Diff）をレポート上で一覧できるようにする。
