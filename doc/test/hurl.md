
#### 1. 網羅の定義（各エンドポイントで最低限作るケース）

各エンドポイントについて、可能な限り以下の観点でケースを用意する。

- 正常系
  - 最小入力（必須のみ）
  - 代表入力（典型的な値）
- 入力バリデーション
  - 必須欠落（400系になるか）
  - 型違い / フォーマット違い（例: UUID不正、日付不正）
  - 範囲外（min/max、limit上限）
- 権限/認証
  - トークンなし
  - 権限不足（403など）
- 存在しないリソース
  - 404（存在しないID）
- 冪等性・二重実行（該当する場合）
  - 同一リクエスト2回で整合が取れるか
- ページング/ソート（該当する場合）
  - `limit=1` `limit=最大` `offset` `cursor`
- 出力のshape
  - 必須キーが存在する
  - null許容が意図通り
  - 配列の要素の最低限のフィールド

#### 2. テストの書き方ルール（hurl）

- assertは「値の完全一致」より「shape/条件」を優先する。
  - 例: `status == 200`、`jsonpath "$..id" exists`、`matches` などを中心
- ただし、仕様として固定すべきもの（enum、ステータス、フラグ）は完全一致で縛る。
- 1ファイル=1ケースに寄せる（PoC段階は読みやすさ優先）。

#### 3. 前提データ（seed）の扱い

- 参照系テストが成立するように、テスト用の固定データを準備する。
- もし固定データが用意できない場合は、
  - `observe/` で取得→fixture化
  - `verify/` はfixture/スタブで成立させる

#### 4. 生成AIにやってほしい作業（手順）

1. リポジトリを解析し、APIのエンドポイント一覧を抽出する。
   - OpenAPI（Swagger）がある場合はそれを最優先。
   - なければcontroller/routerから推定。
2. エンドポイントをグルーピングする。
   - read（GET）/ write（POST/PUT/PATCH/DELETE）
   - 認証必須/不要
   - 外部API依存あり/なし
3. `hurl/coverage.md` を先に作る。
   - エンドポイント × ケース（正常/異常/権限/404…）の表
4. `hurl/verify/` にhurlケースを生成する。
   - まず重要度が高い順（フロント表示に直結、障害が出やすい箇所）
5. 実行方法を `hurl/README.md` に書く。
   - `hurl --variables-file ...` の例
   - レポート出力の例


#### 5. 追加で欲しい情報（AIが不明な場合は質問する）

- テスト環境の `BASE_URL` と認証方式
- テスト用の固定データ（存在するIDなど）
- OpenAPIの有無
